# Traits and Composition

> Part of the language design. `lang-desc.txt` has the overview and the list of documents.

The language does not support traditional class inheritance.

Instead, traits define shared capabilities and reusable default behavior.

A trait is declared like a struct, with no keyword, but has functions and no fields. Its functions without a body must be provided by every conforming struct; functions with a body are defaults.

```
Printable {
  show(self) -> str                         // required
  printLine(self) { print(self.show()) }    // a default
}
```

- A trait signature has no body to infer `self` from, so its methods write `self` or `&self` explicitly. A function without `self` is an associated function, such as `new() -> T`.
- A trait's functions are public (`lang-modules.txt`, "Visibility").

## Example: shared user behavior

```
// file: User.brf

HasUser {
  getUser(self) -> User

  getName(self) -> str {
    self.getUser().name
  }

  getAge(self) -> int {
    self.getUser().age
  }

  getAgeRange(self) -> :adult | :senior {
    self.getAge() |> {
      < 100 => :adult
      >= 100 => :senior
    }
  }
}
```

A struct lists the traits it conforms to after `:`, and writes the required functions among its own. Those functions follow the struct rules: a method is recognized by its use of `self`, so `getUser(self) -> User` in the trait is written `getUser() -> User` in the struct.

A type conforming to `HasUser` only needs to provide the required `getUser()` function to receive the default methods.

```
User: HasUser {
  name: str
  age: int

  getUser() -> User {
    self
  }
}
```

A composed type can reuse the behavior:

```
// file: Admin.brf

Admin: User.HasUser {
  user: User
  tier: int

  getUser() -> User {
    self.user
  }
}
```

Now both `User` and `Admin` support:

```
user.getName()
admin.getName()

user.getAge()
admin.getAge()
```

This avoids repeated method implementations and artificial inheritance hierarchies.

## Conforming to several traits

The traits are joined with `and`, since the struct must satisfy all of them.

```
Admin: User.HasUser and Printable {
  user: User
  getUser() -> User { self.user }
  show() -> str { "admin " + self.user.name }
}

admin.printLine()                  // Printable's default, using Admin's show
```

## Replacing a default

A struct replaces a default by writing a function of the same name. There is no `ovr` keyword.

```
Admin: User.HasUser {
  user: User

  getUser() -> User {
    self.user
  }

  getName() -> str {
    "Admin: " + self.user.getName()
  }
}
```

Default trait methods calling other trait methods resolve to the conforming type's applicable function, including replacements.

Trait-method conflicts and conformance coherence rules still require further specification.

## Trait type parameters

A trait that needs to name the conforming type takes it as its first type parameter. A trait that does not, such as `Printable`, has no parameter.

```
Ord[T] {
  compare(self, other: T) -> :less | :equal | :greater
}
```

The first parameter is never written when conforming: a struct writes `Date: Ord`, and `T` is `Date` in its `compare`.

```
Date: Ord {
  year: int
  month: int
  day: int

  compare(other: Date) -> :less | :equal | :greater {
    ...
  }
}
```

Further type parameters are ordinary and are written when conforming: `Query[T, Item]` is conformed to as `UserCollection: Query[User]`, where `T` is `UserCollection` and `Item` is `User` (`lang-collections.txt`).

## Generics

Generic types and trait bounds are planned as the primary mechanism for reusing algorithms across different types.

Proposed syntax:

```
Collection[T] {
  items: Vec[T]
}

max[T: Ord and Printable](a: T, b: T) -> T {
  a.compare(b) |> {
    :less => b
    _ => a
  }
}
```

Type arguments are proposed to be inferred from a call's arguments, as in Rust, and each generic function compiled once per type it is used with (`lang-desc.txt`, open question 12). How to write functions that exist only for some type arguments, such as a `Collection[T]` whose `T` conforms to `HasUser`, is not decided.

Generics do not imply inheritance or automatically allow unrelated concrete types to be stored interchangeably.
