# Programming Language — Design Overview

> **Status: Experimental language design**
>
> This document describes the intended design and philosophy of a new statically typed, compiled programming language. The syntax and semantics are evolving, and examples should be treated as design references rather than proof of an implemented feature.
>
> These documents describe the next version of the language. The current compiler implements the first version, whose documents are kept unchanged in `docs/v0/` and checked by the document-acceptance tests. `lang-post-0-notes.txt` records the decisions that separate the two.

## 1. Overview

This language aims to combine the **simplicity and expressiveness of modern high-level languages with the performance, predictability, and compile-time safety of systems programming languages**.

Its primary goal is to reduce unnecessary complexity in application development without sacrificing control over data, memory, or program behavior.

The language draws inspiration from Rust, Kotlin, Nim, functional programming, and modern strongly typed languages, but does not attempt to reproduce any one of them.

Key characteristics include:

- Static typing with strong type inference.
- Concise, expression-oriented syntax.
- Modules, structs, traits, and composition instead of class inheritance.
- Automatic reference counting with cycle collection.
- Lightweight borrowing and explicit mutation permissions.
- Explicit copying of nontrivial objects.
- Immutable data through `const`.
- Typed symbols, unions of symbols, and exhaustive pattern matching.
- Pipelines for transforming values and handling results.
- Compiler-enforced recoverable error handling.
- Declarative collection operations instead of unnecessary loops.
- Explicit cleanup of external resources.

The language should make common operations simple while keeping expensive, unsafe, or potentially failing operations visible to programmers.

**Core philosophy: Make the common case concise and the dangerous case explicit.**

## 2. Design Principles

### Simplicity over complexity

The language should avoid introducing multiple ways to accomplish the same task without a meaningful semantic benefit.

Complexity should be managed by the compiler whenever it can do so safely and predictably.

For example, programmers should not manually manage reference counts, write repetitive collection loops, or implement dozens of forwarding methods for related types.

### Expressiveness without hidden behavior

APIs should clearly communicate important behavior, including mutation, error conditions, and expensive copying.

However, internal implementation details should remain encapsulated.

The programmer should understand what an operation guarantees without needing to understand how it is implemented.

### Compile-time safety

The compiler should detect as many mistakes as reasonably possible, including:

- Type mismatches.
- Unhandled recoverable errors.
- Nonexhaustive pattern matching.
- Invalid mutable borrowing.
- Mutation of immutable data.
- Unauthorized access to private fields.
- Incorrect trait implementations.
- Invalid error propagation.

Safety should not require programmers to write excessive boilerplate.

### Composition over inheritance

The language does not use traditional class inheritance.

Instead, functionality is shared through traits, generic programming, and composition.

Types can reuse behavior without becoming subtypes of one another.

### Performance without manual memory management

The language targets native compilation and efficient runtime behavior.

Programmers should not need to manually allocate and release ordinary objects. Memory-management operations are inserted and optimized by the compiler.

Potentially expensive object copies must be explicit.

## 4. Compiler Responsibilities

The compiler is expected to handle much of the complexity that programmers traditionally manage manually.

Its responsibilities include:

**Type checking**
- Static type inference and validation.
- Generic constraint checking.
- Trait implementation verification.
- Typed symbol compatibility.

**Control-flow validation**
- Pattern-match exhaustiveness.
- Error propagation.
- Mandatory acknowledgement of recoverable errors.
- Validation of implicit function returns.

**Memory safety**
- Automatic reference-count operations.
- Retain/release optimization.
- Borrow checking.
- Prevention of mutation through immutable references.
- Protection against invalid ownership and lifetime transitions.
- Integration with cycle collection.

**Encapsulation**
- Module-based visibility.
- Private-field access enforcement.
- Safe object initialization.
- Trait-method resolution and conformance checking.

**Names**
- Casing rules: types, modules and traits start with a capital; everything else starts lowercase.
- Finding modules by name, and reporting a name that matches more than one module.

The compiler should provide actionable error messages rather than requiring programmers to understand internal ownership machinery.

### Compilation strategy

The first compiler is written in C and emits C, which an existing C compiler turns into a native binary.

The long-term goal is to bootstrap: most of the compiler will be rewritten in the language itself, reusing the same C output and runtime.

### Versions

The first version of the compiler handles a single source file and a subset of the language. Its scope is listed in `docs/v0/lang-desc.txt`, "First version", in the first version's syntax: `main()`, the primitive types, `let` and `var`, arithmetic and comparisons, functions with inferred and written return types, `if`, `while`, `for` over ranges, structs and their functions, symbols with `?`, `!` and match blocks, `|>` calls, `print` and the converters, and reference counting without the cycle collector.

The next version moves that scope to the syntax and rules in these documents. Which further features it adds, such as arrays and vectors, modules found by name, and `const`, is planned in `docs/plans/`.

These come later: lambdas and `Fn`, the collection functions, named tuples, maps, traits, generics written by the programmer, and the cycle collector.

## 5. Features Still Under Consideration

The following areas are not fully specified and should not be assumed to have final behavior:

1. Enforcing `const` for values returned by calls that are still referenced elsewhere, and for mutable objects stored inside a `const` value. Storing a `const` or read-only reference is already prevented (`lang-memory.txt`, "Storing references").
2. Shallow versus deep cloning rules.
3. Trait coherence and conflict resolution.
4. Weak-reference syntax and runtime representation.
5. Scoped resource cleanup such as `defer`.
6. Async programming and concurrency.
7. ABI and foreign-function interfaces.
8. Catching a misspelled symbol tag in a function whose return type is inferred.
9. Whether a type can conform to a trait outside its defining module, and how built-in types such as `int` conform to traits.
10. Nested modules, for which the `mod` keyword is reserved.
11. How a type of your own converts with `str(value)`, the other converters, and string interpolation.
12. Generic functions: bounds such as `max[T: Ord and Printable](a: T, b: T)`, inferred type arguments, and compiling one copy per type.

These are design questions rather than commitments to specific implementations.

## 6. Guidance for Coding Agents

When implementing or extending this language, follow these principles:

- **Preserve simplicity.** Prefer extending existing abstractions over introducing overlapping syntax.
- **Avoid inheritance.** Use traits, composition, and generics for behavior reuse.
- **Keep borrowing lightweight.** Retain `&` for mutable access and ordinary type parameters for immutable borrowing.
- **Keep memory management automatic.** Use ORC; do not introduce manual reference-count requirements into ordinary application code.
- **Never silently clone objects.** Use explicit `.clone()` for independent object duplication.
- **Preserve `const` guarantees.** Do not allow mutation through shared aliases or returned references.
- **Enforce recoverable errors.** Do not allow fallible operations to be silently discarded.
- **Keep `|>` generic.** The pipeline transfers values; pattern matching handles destructuring and branching.
- **Favor declarative collection operations.** Avoid repetitive loops when an existing iterator clearly expresses the operation.
- **Maintain module privacy.** Types are always public but may still have private fields and controlled construction.
- **Keep external resource cleanup explicit.** Do not rely on GC timing to close files or connections.
- **Do not assume unresolved features are finalized.** When implementing an ambiguous case, identify the required semantic decision rather than inventing an implicit guarantee.

Examples in these documents describe the intended language behavior. They are not necessarily executable in the current compiler.

---

## Long-Term Vision

The language aims to occupy a middle ground between traditional systems languages and high-level application languages.

It seeks to offer the control and static guarantees associated with Rust, the convenient abstractions of Kotlin and modern functional languages, and the automatic memory management of Nim's ORC model.

The programmer should focus primarily on **what the program does**, while the compiler handles routine memory management, type checking, borrow validation, and error-safety enforcement.

The ultimate goal is a language that is expressive enough for everyday application development, predictable enough for performance-sensitive software, and simple enough that developers can understand its behavior without mastering a large collection of special rules.
