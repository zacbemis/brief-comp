# Memory, Borrowing, and Resources

> Part of the language design. `lang-desc.txt` has the overview and the list of documents.

## Memory Management

The language uses **Nim-inspired ORC (automatic reference counting with cycle collection)**.

The goal is predictable, efficient memory management without requiring programmers to manually allocate and release ordinary objects.

### Reference semantics

Objects use shared-reference semantics by default.

```
let user = User.new("Bob", 20)!
let other = user
```

Both variables refer to the same underlying object.

This does not duplicate the entire object.

The compiler automatically manages reference counts.

### Copying

Lightweight value types, such as primitives, are copied implicitly.

```
let a = 10
let b = a
```

For larger objects, independent duplication requires an explicit operation.

```
let copy = user.clone()
```

`.clone()` is intended to produce an independent copy, rather than merely incrementing a reference count.

The precise shallow/deep-copy behavior for nested references is still being specified. Cloning for immutable snapshots must not leave mutable aliases capable of changing supposedly immutable data.

### Reference counting

The compiler inserts and optimizes reference-count operations.

Programmers do not manually call `retain()` or `release()`.

The compiler may eliminate unnecessary operations through ownership transfer, escape analysis, and lifetime analysis.

Passing an object to a plain parameter is a borrow. When the compiler can prove the caller's reference stays alive for the whole call, no count needs to change.

M4's initial ownership pass is conservative: reference-valued reads produce owned
temporary snapshots. This pins field arguments even if a later argument or the
callee overwrites their owner's field. The callee still borrows its parameters;
returned references are owned. Stores retain the new value before releasing the
old one, including self-assignment. Locals and temporaries are released on lexical
scope exits, returns, break, and continue; reused loop slots release their previous
values. Lifetime/count elimination is a future optimization.

```
getAge(user: User): int {
  user.age
}

let user = User.new("Bob", 20)!
let age = getAge(user)   // no count change: user outlives the call
```

The count goes up when a function stores the object somewhere that outlives the call. A function that keeps an argument takes it as `&` ("Storing references" below).

```
pub add(collection: &UserCollection, user: &User) {
  collection.userVec.add(user)   // the vector now holds its own reference
}
```

### Cycle collection

Ordinary reference counting cannot reclaim unreachable objects that strongly reference one another.

The language addresses this through an automatic cycle collector inspired by Nim ORC.

This allows cyclic object graphs to be reclaimed without requiring programmers to manually break every cycle.

Weak references may also be provided for explicitly non-owning relationships.

The compiler works out from the type definitions which types can be part of a cycle. A type can only be part of a cycle if a value of that type can reach another value of the same type.

```
pub User {
  name: str
  age: int
}

// A User holds no reference that leads back to a User.
// It can never be part of a cycle and the collector never looks at it.
```

```
pub Node {
  value: int
  next: Sym<:ok(Node), :none>
}

// A Node can reach another Node, so two nodes can point at each other.
// The collector checks Node objects.
```

A `str` holds no references and can never be part of a cycle.

### Order of implementation

The first compiler implements reference counting without the cycle collector. Until the collector exists, objects that form a cycle are not freed. Objects that do not form a cycle are freed as soon as their last reference goes away.

### Current concurrency scope

The initial language design targets single-threaded execution.

Multithreaded ARC, synchronization, and cross-thread borrowing rules are intentionally deferred.

## Borrowing and Mutation

The language uses lightweight borrowing rules rather than requiring programmers to manage ownership manually.

### Immutable borrow

An ordinary object parameter represents immutable borrowed access.

```
getAge(user: User): int {
  user.age
}
```

The function can inspect the object but cannot mutate it through that parameter.

### Mutable borrow

The `&` operator represents a mutable borrow.

```
setAge(user: &User, age: int) {
  user.age = age
}
```

The caller does not need to explicitly transfer ownership.

`&` grants writable access, not exclusivity. A plain parameter and direct aliases
read from it have read-only access. A `&` parameter grants writable access.

Other references to the same object may exist while it is borrowed.

In the current compiler, `&` parameters require a struct type. The caller writes
an ordinary argument; `&` appears only in the parameter declaration. The parameter
binding itself remains immutable. Field paths rooted in an ordinary parameter
cannot be written or forwarded to an `&` parameter. Reading a struct reference
from that parameter, or from its fields, preserves read-only access when bound
to `let` or `var`, copied again, selected by a branch, or assigned to a local.
Retaining a reference does not upgrade its permission. Copied primitive values
are independent and do not carry this restriction.

A `var` binding can be rebound; its current reference's permission follows the
new value. Rebinding restores writable access only when the new value has no
propagated read-only restriction.
At control-flow joins, access is read-only if any continuing path is read-only.
Loops conservatively include zero iterations and backedges; `break`/`continue`
states are included, and returning paths do not restrict continuing paths.

A struct call result is read-only when it could hold an object from a
read-only argument (including the receiver): when some struct type can be
reached, through fields, both from the result's type and from that argument's
type. The compiler works this out from the type definitions, as it does for
cycles. An identity call `same(p)` and a getter returning `q.p` stay
read-only. `Report.new(q.user)` stays read-only if a `Report` can contain a
`User`, and is writable if it holds only strings and numbers. Owning the
returned reference does not upgrade access.

A struct literal with any read-only struct initializer is read-only as a whole,
including its other fields. Primitive results and copied primitive fields do
not carry the restriction.

### Storing references

A read-only struct cannot be stored in a field. Whoever can write the holder
could later change the stored object, so storing would turn read-only access
into writable access. A function that keeps an argument takes it as `&`, which
tells its callers that the object may be changed later.

```
attach(report: &Report, user: User) {
  report.owner = user          // Compiler error: user is read-only; take it as &User
}

attach(report: &Report, user: &User) {
  report.owner = user          // allowed
}
```

The rule covers every path to the store: a local alias, a call result that
could hold the argument, and a literal built from it. A caller holding only a
read-only value cannot pass it to `attach`; it needs a value it may change,
such as a fresh object or, once cloning exists, a copy.

This is an access-path rule, not a purity promise or transitive `const`.
Other writable aliases can still change the data. M4 does not implement
`const` or cloning.

### Shared aliases

Multiple references to an object are allowed.

```
let user = User.new("Bob", 20)!
let other = user
```

The presence of multiple references does not, by itself, prohibit mutation.

Borrowing does not forbid shared aliases. Read-only access does not freeze the
object; only `const` guarantees that no reference can mutate it.

### Immutability

`const` represents immutable data, not merely an immutable variable name. Nobody can mutate a `const` object, through any reference.

```
const user = User.new("Bob", 20)!
```

Mutation through the immutable object or references derived from it must be prohibited.

A `const` cannot be initialized from an existing `let` or `var` binding. This is a compile error that tells the programmer to either clone the value or change the `const`.

```
let user = User.new("Bob", 20)!

const frozen = user  // Compiler error
```

The compiler never silently freezes or copies the object. The programmer must explicitly create an independent copy.

```
const frozen = user.clone()
```

A `const` value can only be assigned to another `const` binding or passed to a parameter that is not `&`. Assigning it to a `let` or `var` binding, or passing it to a `&` parameter, is a compile error.

```
const user = User.new("Bob", 20)!

let other = user     // Compiler error
setAge(user, 21)     // Compiler error: setAge takes &User
```

The compiler must ensure that immutable objects cannot be mutated through hidden aliases, including aliases to nested data.

A call that receives a `const` argument returns a `const` result. The result may contain objects from the argument, so letting it go into a `let` or `var` would allow them to be changed.

```
const users = loadUsers()!

let first = users |> first()          // Compiler error: the result is const
const first = users |> first()        // allowed
let total = users |> count()          // allowed: an int is copied
```

This is sometimes stricter than needed, for example when the call builds entirely new objects.

`const` is enforced at compile time. Two cases are outside what that check can see and are not yet handled:

- A value returned by a call that is still referenced elsewhere, as in `const dog = kennel.first()`.
- A mutable object stored inside a `const` value, as in `const kennel = Kennel.new(dog)`.

A `const` value passed to a function that stores it in a mutable object is already prevented: a `const` can only reach an ordinary parameter, where it is read-only and cannot be stored ("Storing references").

## Resource Management

Memory and external resources are managed separately.

ORC is responsible for ordinary memory reclamation.

Resources such as files, sockets, database connections, and transactions require explicit lifecycle management.

Example:

```
let file = File.open("data.txt")!

let contents = file.readAll()!

file.close()!
```

The language should not rely on cycle collection or object destruction to determine when important external resources are closed.

A future scoped-cleanup mechanism, potentially `defer`, may help ensure resources are explicitly closed on every exit path.

Resource cleanup errors must not be silently ignored.
